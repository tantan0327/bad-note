**リンク色の扱い**(2026-08-22、2026-10-18 に追記) —— `NavigationLink` / `Button` のラベルは

**`.buttonStyle(.plain)` を足して初めて本文の色になる。**

### デザインの決めごと(2026-08-22。両 OS × ライト / ダークで実機確認済み)

**色**:

- **ブランド色はインディゴ**(light `#5C6BC0` / dark `#7986CB`)。`AccentColor` は
  `Darwin/Assets.xcassets` と `Sources/BadNote/Resources/Module.xcassets` の 2 か所にあり、
  **値は同じに保つ**(Android に効くのは Module 側だけ。開発メモ「色は asset catalog 経由…」参照)
- **色は `View/Palette.swift` の 8 トークンから取る** —— `accent` / `surface` / `surfaceRaised` /
  `done` / `closer` / `next`。実体は `Module.xcassets` の colorset(light / dark の 2 値)なので、
  色替えは JSON を直すだけで両プラットフォームに効く。**View で色を直書きしない**
- **手応えは色 + 形** —— できた = 塗り丸(緑)/ 近づいた = 輪(琥珀)/ 次にやる = 四角(青)/
  記録なし = 小さな灰点(課題詳細の進み方)。色だけに頼らない

**文字の段階**(役割 → フォント。新しい文字はこの表から選ぶ):

| 役割 | フォント | 例 |
|---|---|---|
| 画面の主役(その画面の固有名) | `.title2` | 課題名(できている状態)、大会名、めざす姿の本文 |
| 画面の主数字 | `.system(size: 34, weight: .semibold)` | 残り日数(ホーム・大会詳細) |
| セクション見出し | `.headline` | 「今週の重点」「もとの言葉」 |
| セクション内の小見出し | `.subheadline` | 振り返りの種目名 |
| 本文・一覧の行タイトル・引用 | `.body`(既定) | 課題の行、もとの言葉の原文 |
| 補足・メタ情報・小さな導線 | `.footnote` | 日付、件数、「編集する」 |
| チップ・バッジ・注釈 | `.caption` | 習熟度チップ、入力の説明文 |
| カード内の統計数字 | 22pt semibold(単位・ラベルは `.caption`) | `View/StatItem.swift`。積み上げの 2 スタット、課題詳細の記録 |
| 積み上げの主数字 | `.system(size: 40, weight: .bold)` | `View/StatsView.swift` の通算時間。**この画面に 1 つだけ** |

詳細画面のタイトルは**その画面の固有名**(課題名・大会名)を inline で出す。
「課題」「大会」のような中身の無い大タイトルは出さない
(`.navigationBarTitleDisplayMode` は macOS 不可 → `#if os(iOS) || os(Android)` で囲む)。
一覧系の大タイトル(課題 / 大会 / 設定など)は中身を表す言葉なのでそのまま。
例外 —— 練習時間入力の分数(52pt)は入力部品の表示で表の外。

**日付の出し方** —— **画面に出す日付は必ず `View/DateText.swift` を通す。**
`formatted(date:time:)` は**端末のロケール依存**で、日本語以外の端末だと
「Aug 15, 2026」と英語が混ざる(使用箇所はゼロに保つ)。用意してあるのは 2 つだけ:

| 関数 | 形 | 使う場面 |
|---|---|---|
| `DateText.day(_:asOf:)` | 「8月24日」 | 一覧やメタ情報(課題の作成日、アーカイブした日) |
| `DateText.dayWithWeekday(_:asOf:)` | 「8月24日(月)」 | **その日そのものが主役**(家トレの見出し、大会の開催日) |

- **年は今年と違うときだけ出す**(「2027年2月20日(土)」)。常に出すと冗長で、
  出さないと去年の記録が今年のものに見える。目標大会は半年先=翌年になることが多い
- **例外 1: `DateText.month(_:)`(「2026年9月」)は年を常に出す** ——
  カレンダーは何か月も先へ送れるので、年が無いと現在地が分からない
- **例外 2: カレンダーのセルの数字は `Text(verbatim:)`** —— 書式を持たないので
  `DateText` を通さない。ただし `accessibilityLabel` は `DateText.dayWithWeekday` を通す
- **OS が描く日付ピッカーは対象外**(上のプラットフォーム差の線引きに従う)

**面と余白**(新しい面はこの 3 種類から選ぶ):

| 部品 | 形 | どこで決まるか |
|---|---|---|
| カード | 面 `Palette.surface` / 内側 12 / 角丸 8 / 幅いっぱい | `View/Card.swift`(`Card { ... }`)。強調の帯は `Card(background: Palette.surfaceRaised)` |
| バッジ(表示のみ) | `.caption` / 横 8 縦 4 / 角丸 4 / `Palette.surfaceRaised` | `View/Badge.swift`。押せる部品には使わない |
| ピル(押せる絞り込み) | `.footnote` / 横 12 縦 8 / 角丸 16 | 課題一覧の絞り込み行のみ |
| 行の習熟度 | ミニ 4 分割バー + `.caption` の段階名 | `View/MasteryIndicator.swift`。課題詳細のバーの縮小版 |
| カレンダーのセル | `.footnote` / 高さ 40 / 角丸 8 / 幅は 7 等分 / 登録済みは `Palette.accent` 塗り | `View/PracticePlanView.swift`。列の間隔 2 は 4 の倍数の例外(幅が足りない) |

- **動き** —— 選択・チェック・バーの伸縮 = `Motion.select`(easeOut 0.15)、
  行の移動・出入り・画面の切り替わり = `Motion.move`(easeInOut 0.3)。
  `View/Motion.swift` から取り、duration を直書きしない
- **`accessibilityIdentifier` の命名** —— kebab-case で「画面-部品(-id)」
  (`home-record` / `issue-row-3` / `practice-kind-whole`)。操作可能な View には必ず付ける
- **キーボードを閉じる手段は iOS だけに置く**(2026-10-11)—— `numberPad` には改行キーが
  無いので、iOS では `@FocusState` + `ToolbarItemGroup(placement: .keyboard)` の「完了」を出す。
  **Android には出さない** —— システムの戻るで閉じるのが作法で、しかも **SkipUI は
  `.keyboard` 配置を既定(= ナビゲーションバーの右)に流す**ので、出すと常設の
  ボタンになってしまう(`Commands/Toolbar.swift` の `Evaluate` に `.keyboard` の分岐が無い)。
  `#if os(iOS)` で `@FocusState` の宣言ごと囲む
- **並べ替えは表示だけ。保存順は書き換えない**(2026-10-11、仕様書 §3.3)——
  課題一覧の並び替え(手動 / 放置が長い順 / 影響度が大きい順 / 習熟度が高い順)は
  `Logic/IssueSort.swift` の純粋関数で、**読んだ後に表示だけ入れ替える**。
  SQL の `ORDER BY` は `sort_order, id` のまま触らない —— 変えると
  「保存された順」と「いま見えている順」の区別が付かなくなる。
  **手動以外では長押しドラッグを止める**(`moveDisabled`)——
  見えている順と保存順が違うまま落とすと、指を離した場所と違う位置に入る。
  スワイプの上げ下げは `FocusBoard` が保存順から数え直すので、どの並びでも使える。
  名前には**向きを入れる**(「影響度」ではなく「影響度が大きい順」)
- **`Spacer` を挟んだ行は、面を敷かないと押せない**(2026-10-18 に実機で踏んだ)——
  `Button` の当たり判定は**ラベルが実際に描いた所だけ**。`HStack { Text; Spacer; Text }`
  の中央は何も描かないので、**文字の真上を狙わないと反応しない**。
  層の見出しがこれで、畳みの機能は事実上操作できなかった。
  **`contentShape` は SkipUI で使えない**(`@available(*, unavailable)`)ので、
  `.frame(maxWidth: .infinity)` + `.background(Palette.surface)` で面を 1 枚敷く。
  **読むだけでは見つからない。** 行全体を押す部品を作ったら必ず実機で中央を押す
- **「空」と「絞り込んで 0 件」を混ぜない**(2026-10-18)—— 絞り込みは SQL 側で効くので、
  該当 0 件でも中身は空になる。これを初回の案内に化けさせると
  **絞り込み行ごと消えて、解除する手段が無くなる**(再起動以外に戻れない)。
  空状態を出すときは「解除」の導線を必ず残す
- **見えている範囲だけで並びを焼き付けない**(2026-10-18)—— 絞り込み中に
  「この並びで整理」を押すと、隠れている課題の `sort_order` と衝突する。
  **絞り込み中はボタンを出さず、モデル側でも弾く**(画面を 1 つ増やすたびに
  押せる経路が増えるので、判断は両方に置く)
- **畳んだ層に入ったものは見せる**(2026-10-18)—— 前回より件数が増えた層は開く。
  課題を追加すると「いつか」に入るので、畳んだままだと
  **件数が 1 増えるだけで行がどこにも出ない**。「書いたのに見つからない」は
  未整理セクションを作ってまで潰した失敗で、同じ穴を自分で開け直していた
- **「見る順」と「整理する順」をつなぐ**(2026-10-12)—— 並び替えは表示だけで、
  その間は長押しドラッグが止まる。一方、手動の並びは実質「登録が古い順」。
  **どちらのモードでも優先順に整理できなかった**ので、
  「この並びで整理」で**見えている順を保存順に焼き付ける**(`Logic/IssueOrderCommit.swift`)。
  押したあとは手動に戻るので、そこからドラッグで微調整できる。
  **変わったものだけ書く** —— 全件書くと動いていない課題の `updated_at` まで新しくなり、
  §4.2 の stale 判定がリセットされる。
  自動では決して書き換えない、という §3.3 の約束は変えていない(仕様書に追記済み)
- **層は見出しを押して畳める**(2026-10-12)—— 「いつか」が 8 件を超えていれば最初から畳む。
  40 件が開いたまま並ぶと一覧が 1 本の長いリストになり、上の 2 層が視界から消える。
  **畳んだ層にもドラッグの落下先(placeholder)を 1 つ残す** ——
  空の層で同じ失敗を踏んでいる(落とし先が無いと運び込めない)。
  件数は畳んでいても見出しに出すので、隠れた数は分かる
- **並び替えの基準は行にも出す**(2026-10-12)—— 放置が長い順で眺めているときだけ、
  行に最後に触れた日を添える。どれくらい放置したのかが行から読めないと、
  並びを信じるしかなくなる。**常設はしない**(他の並びでは判断材料にならない)
- **課題を書く欄は常に 1 つ**(2026-10-12)—— 追加・編集・整理のどの画面でも、
  文章を書く欄は「課題」1 つだけにする。
  **追加が 1 欄で編集が 2 欄**(しかも片方が空)だと、「さっき書いたのに
  まだ書く欄がある」と見えて、入力が面倒に感じられる。
  仕組みは変えていない —— **直した 1 行は言い換え(`doneForm`)に入り、
  書き留めた言葉(`coachWords`)は残る**(`Logic/IssueTitleEdit.swift`)。
  元の文に戻したら言い換えは持たせない(同じ文を 2 つ持つと詳細が同じ行を 2 度出す)。
  もとの言葉は**折りたたみの中**と課題詳細の引用でだけ見せる
- **任意の項目は畳んでおく**(2026-10-12)—— 種目 / 習熟度 / 影響度 / コスト / タグは
  すべて任意で既定値があり、後から変えられる。同じ重さで並べると
  **記入必須のフォームに見える**ので、「くわしく決める(任意)」の
  `DisclosureGroup` に入れて既定は閉じる。
  追加は 1 行書いて保存、整理は読んで 3 択を押すだけで終わる
- **探す場所では動かさない**(2026-10-11)—— 検索中の行にはスワイプもドラッグも持たせず、
  タップして詳細で決める。検索は 3 層をほどいた 1 本の並びなので、
  層の上げ下げをその場でやると**どこに動いたかが画面から消える**。
  行には居場所(重点 / 次にやる / いつか / 未整理)のバッジを添えて、今いる場所だけ伝える
- **保存できない理由は必須の欄の直下に出す**(2026-10-11)—— 保存はツールバーにあり、
  エラー文を画面最上部に置くと、下までスクロールして押した人には見えない。
  `canSave` で保存を `.disabled` にし、理由は欄のすぐ下に `.caption` で添える
- **プラットフォーム差の線引き**(2026-08-24 決定)——
  **アプリのアイデンティティは共通トークンで揃え、OS 標準部品の見た目は各 OS に委ねる。**
  揃える側: 色(Palette)/ 文字の段階 / 面と余白(Card・Badge ほか)/ 動き(Motion)/
  アイコン(.symbolset)/ 文言。委ねる側: ツールバー・日付や時刻のピッカー・スイッチ・
  リストの作法など OS が描く部品(Skip の既定どおり)。
  **例外は「差が誤解や操作ミスを生む」場合だけ**個別に対応する(今は該当なし)
- **間隔は 4 の倍数だけ**(`4` / `8` / `12` / `16` / `20` / `24`)
- **余白は 2 段階** —— 画面の外周は `.padding()`(= 16)、カードの内側は `Card` が持つ 12
- **区切り線** —— 同じ形の行を選ぶだけの画面 = `List`(設定 / 課題一覧 / 組み替えモード /
  大会一覧 / アーカイブ / 家トレ)。役割の違うブロックが縦に並ぶ画面 = カード
  (ホーム / 課題詳細 / 大会詳細 / 練習ログ入力 / インボックス整理)

**課題の出口は 3 つ**(2026-10-11 に 1 つ足した)—— **定着**(`archived`。Lv.4 で「克服した」。
積み上げの数字に入る)/ **見送り**(`shelved`。棚卸しかホームの「もう不要」。**積み上げには入らない**)/
**削除**(未整理の整理フロー内だけ)。**定着と見送りを分けてあるのが肝** ——
ひとつにすると、興味を失った課題を外すたびに「定着した課題」が増えて達成の数字が嘘になり、
嘘になるくらいならと外さなくなって課題が減らなくなる。
見送りは設定の「見送った課題」から戻せる(段は下げない)。

**通知**(§8)は 3 種類とも実装済み(練習前 / 大会当日の夜 / 週 1 回)。
**練習前の通知は曜日ではなく登録された練習予定日に出す**(2026-08-31。予定日を
入れていなければ鳴らない)。**1 日 1 通まで**で、
重なったときの優先は **大会 → stale → 練習前**。繰り返しトリガーではなく
21 日分を毎回入れ直す方式(繰り返しだと 1 日 1 通の制御ができない)。既定は off。

**課題一覧**(§7.4)は §7.4 の 3 つの方法すべてを実装済み ——
**長押しドラッグ**(層をまたぐ移動と層内の並び替え)/ **スワイプ**(右で 1 段上げ / 左で 1 段下げ)/
**週次の組み替えモード**。加えて**絞り込み行**(種目 / 習熟度 / タグ、既定はフィルタなし)。
種目の絞り込みは `both` の課題も含める(§3.5)。

ドラッグは 3 層を見出し行込みの 1 本の `ForEach` に畳んで実現している
(`onMove` はひとつの `ForEach` 内でしか働かないため)。落下位置から層と位置を求めるのは
`TierLayout`。**この構造を崩すとドラッグが壊れる。**

**タブ構成** — **ホーム / 家トレ / 課題 / 大会** の 4 つ(2026-08-22 実装)。
タブは「往復するもの」だけに絞る。家トレ(§10)は毎日開く画面なのでホームの隣。

- 練習ログ入力はホームのボタンからシート(§7.2 のヘッダーが ✕ / 保存 のモーダル)
- 課題詳細は課題一覧からプッシュ
- 設定は日常操作ではないのでホームのツールバー(歯車)。
  stale の閾値・通知時刻・アーカイブ閲覧の置き場になる

テンプレート(`WelcomeView` / `ItemListView` / `ViewModel.swift` / `Item`)は削除済み。

## 課題を減らす仕組みの決めごと(2026-10-11〜10-19。`tasks.md` から移した)

実際に使って「課題が溜まって減らない」という報告を受けて作った部分。
**一覧の見せ方ではなく出口の構造の問題だった。**

### 課題が能動リストから外れる道

| 出口 | 条件 | 実装 |
|---|---|---|
| 克服した | 習熟度 4 のみ。アーカイブなので戻せる | `IssueDetailModel.overcome()` |
| 見送る | 棚卸しの 3 択。達成ではないので積み上げに数えない | `IssueStatus.shelved` |
| もう不要 | その週に再浮上した課題のみ。アーカイブ | `HomeModel.archiveStaleIssue(_:)` |
| 削除 | 課題の編集画面の末尾。戻せない | `IssueEditModel.delete()` |

**見送る(`shelved`)と定着(`archived`)は別物。** 積み上げの「定着した課題」は
`archived` だけを数えるので、見送っても達成の数字は増えない。再浮上の対象からも外れる。
設定の「見送った課題」から戻せるが、**戻すときに段は下げない** ——
定着からの再浮上と違い、見送りは何も達成していないため。

**`status` は CHECK の無い TEXT 列**なので、値を足すのにマイグレーションは要らなかった。

### 入口は絞らない。直すのは出口だけ

書き留めるのを面倒にするのは、このアプリの前提(コーチの言葉を忘れる、を解決する)を壊す。
課題数の上限や登録の抑制は入れない。

### 並び替え・検索・整理

- **並び替えは表示だけ**(仕様書 §3.3)。手動 / 放置が長い順 / 影響度順 / 習熟度順
- **「この並びで整理」は本人が押したときだけ**保存順に焼き付ける。
  **変わったものだけ書く** —— 全件書くと `updated_at` が動き、
  §4.2 の stale 判定(最終更新からの日数)が全部リセットされる
- **絞り込み中は「この並びで整理」を出さない。** 見えている課題にだけ番号を振ると
  隠れている課題の `sort_order` と衝突し、解除した瞬間に取り消せない並びになる
- **検索するのは課題の言葉だけ** —— できている状態 / もとの言葉 / コーチ名。
  言い換えを持っていても原文で引ける。**検索中は 3 層をほどいて 1 本にする**
  (どの層にいるか思い出せないから探している)。未整理も混ぜ、行に居場所のバッジを添える
- **探す場所では動かさない。** 検索結果にスワイプもドラッグも持たせず、タップして詳細で決める
- **ひらがな / カタカナの読み替えはしていない** ——「れしーぶ」では「レシーブ」に当たらない
- **放置が長い順のときだけ、行に最後に触れた日を出す。**
  並びの基準が行から読めないと、並びを信じるしかなくなる
- **層は畳める。**「いつか」が 8 件を超えていれば最初から畳む。
  **畳んだ層にも落下先を残す**ので、ドラッグで運び込める。
  前回より増えた層は自動で開く(保存直後の課題が見えないため)

### 棚卸し(月 1 回)

対象は「いつか」を放置が長い順に、**1 回 10 件で打ち切る**(終わらない棚卸しはやられない)。
出口は 残す / 次にやるへ / 見送る の 3 つ。

- **強いボタンは置かない** —— 捨てる側を押しやすくすると、アプリが減らすほうへ背中を押すことになる
- 誘うのは「いつか」が 10 件以上あって、前回から 30 日経ってから
- ホームにカードを 1 枚出すだけ。**件数も警告も出さない**(§5.3)
- 「またにする」でも次は 30 日後。毎回開くたびに誘わない
- **通知は足していない**(1 日 1 通の枠は埋まっている)
- 残した課題は翌月また出る。忘れているものを順に見せるのが目的なので隠さない
- **設定にも入口を置く** —— ホームのカードは月 1 回しか出ないので、それが無いと間が空く

### 入力の手間

画面ごとに欄の数が変わっていたのが面倒さの正体だった(追加 6 ブロック / 編集 7 ブロック)。

- **書く欄は 1 つだけ。** 追加でも編集でも「課題」の 1 欄。
  直した 1 行は言い換え(`doneForm`)に入り、書き留めた言葉(`coachWords`)は残る。
  **データの持ち方は変えていない**
- **比較の基準は「画面を開いた時点の 1 行」。** 新しい `coachWords` と比べると、
  もとの言葉の誤字を直したときに直す前の文が言い換えに入る
- 種目 / 習熟度 / 影響度 / コスト / タグ ともとの言葉は
  「くわしく決める(任意)」の折りたたみの中。既定は閉じる

### 詳細画面の導線

- **編集は右上。** 折りたたみの中に置いたら見つからなかった(2026-10-18 に報告を受けた)
- **右上に「⋯」を並べない。** 文字のボタンと記号のボタンが隣り合うと 1 つに見える
- **削除は編集画面の末尾。** 連絡先やカレンダーと同じ場所で、
  一覧 → 詳細 → 編集 と 2 つ入った先なので §7.5 の「気軽に消せる場所に置かない」を満たす。
  確認には**何が消えるか**を書く(手応えは一緒に消え、練習の記録は残る)
- 削除後は課題詳細に戻るので、中身を出さず「この課題は削除しました」だけ出す

### 使い始めの画面(2026-10-27)

デモデータを消して 4 タブを見直して決めたこと。
**それまでの確認はすべてデモデータ入りで、初見の画面を一度も見ていなかった。**

- **`List` の中では `NavigationLink` が必ず行(シェブロン付き)になり、
  `.buttonStyle(.borderedProminent)` が効かない。**
  空状態でボタンの姿にしたいなら、`List` を使わず素の `VStack` で出す。
  課題 / 大会 / 家トレの 3 タブはこの形で揃えてある
- **1 件も無いときは、その状態でしか使わない部品を出さない。**
  課題タブの検索バー(探す相手がいない)、家トレの日付切り替え(記録するものが無い)。
  層と絞り込み行は 2026-10-11 に入れたが、この 2 つが漏れていた
- **ほんとうの初回(`HomeModel.isJustStarting` = 課題も練習ログも無い)は、
  塗りつぶしボタンを 1 つに絞る。** このアプリの入口は「気づいたことを 1 行書く」。
  大会の登録と練習の記録は枠線に落とす。1 件でもできたら元に戻す
- **ツールバーの言葉は画面の中と揃える。**「追加」だけだと、
  画面から目を離したときに何を追加するのか読めない
  (課題を書く / 大会を登録する / メニューを作る)

### 課題の書き方を迷わせない(2026-10-28)

**「できていないことを書くのか、できている状態を書くのか分からない」**という声が出た。
原因は入力欄の 1 文だった。

> 「〜できている」の形で書くのがおすすめです。言われた言葉のままでも構いません

**勧めたうえで許すと、勧められていないほうが間違いに見える。**
しかも助言が抽象的なので、手元の「面が寝てる」をどう扱えばいいか判断できない。

仕組みのうえでは**どちらでも本当に動く** ——
捕まえる場所(課題を追加 / 練習ログの追加する課題)は `coachWords` に入れるだけで、
完了形への言い換え(`doneForm`)は整理の画面で**任意**として足せる。
UI の言い方だけが設計とずれていた。

**かといって「どちらでもいい」と平らに言うと、設計の向きが消える。**
一覧の主表示は完了形(`displayTitle` は `doneForm` を優先する)で、
前向きな見え方を保つための決めごと(CLAUDE.md)。
最初に「どちらの書き方でも大丈夫です」とだけ書いたが、それでは完了形に寄せる理由が
どこにも無くなるので戻した。

**出す順番がそのまま意味になる。**

1. 「一覧には「できている形」が出ます」—— **何が起きるかを先に言う。**
   勧めるのではなく、事実を言う(§5.3 アプリは解釈や警告を出さない)
2. 変換を実物で 1 組だけ見せる —— 言われたまま / できている形。
   同じ灰色の文を 4 行並べたら読み分けられなかったので、例は `Card` の面に載せ、
   ラベルを `.caption`・例文を `.footnote` にして段差をつける
3. 「書いたままでも保存できます。あとから直せます」—— **逃げ道は最後に置く。**
   先に書くと、逃げ道のほうが本筋に見える

そのほか:

- **出すのは追加のときだけ**(`model.isNew`)。編集で開く人はもう書き方を知っている
- **プレースホルダは「言われたまま」にする。** 捕まえる瞬間に手元にあるのは
  言われた言葉そのもの。完了形を例に出すと、その場で言い換えを考えさせることになる。
  練習ログの「追加する課題」も同じ理由で「例: 面が寝ていると言われた」に揃えた
- **あとから直す道は既にある。** 既存の課題で「課題」の 1 行を直すと
  `doneForm` に入る(`IssueTitleEdit.applied`)。課題詳細の右上「編集」から 1 タップ。
  **完了形にしていない課題を名指しで促すことはしない** —— §5.3 に反する
